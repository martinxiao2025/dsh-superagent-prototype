# 003 执行

本文跟随一个已接受的工单走过执行、交付与恢复。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每个开启的工单有一个阶段，由它在等待什么决定。自上而下读表；第一个匹配的行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递一个输入失败；2 秒后重试，随后按加倍延迟直到一分钟；一次成功、一次新的派工或工单结束都会清除它 | 输入未送达 |
| person / answer | 它有一个待人工决定 | 等待回答 |
| person / review | 最新报告为 `ready` | 等待评审 |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | 受阻 · 失败 |
| working / queued | 没有派工，或有一个待启动的 | 排队中 |
| idle | 最新报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其余一切 | 执行中 |

`person` 阶段意味着工单没有人的输入就无法继续。一条新的人的消息会把 `blocked` 或 `failed` 的工单交还其执行器，于是它进入下一个匹配的阶段，通常是 `working`。

`idle` 工单已结束回合且没有未决问题。已订阅线程上的一个触发可以延续它。

## 执行器

每个工单得到一个名为 `worker-<ticket id>` 的执行器 Session 和一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认 `<stateDir>/work`。

执行器 Session 以运维者的操作系统用户身份不经批准地运行命令。它们的 `dsh-superagent-cn-worker` preset 包含工作所需的工具，并在前台 shell 命令运行 5 秒后将其转入后台任务。这让执行器在下一步就能收到新消息，而不必等待长命令结束。

主 Session 使用 `dsh-superagent-cn-router`，同样的 5 秒 shell 与任务等待限制，以及更小的路由工具集。Session 保留创建时选择的 preset。执行器的子代理使用 DeepSeek Harness 的 `standard` preset。

### 后台工作与执行器槽位

当回合结束时仍有 shell 任务或子代理在运行，工单保留其执行器槽位并保持执行中。它不会被上报为等待，主 Session 也不会收到等待报告。完成的任务或子代理会在同一槽位内以其结果唤醒执行器。一旦某个回合结束时没有后台工作，执行器就正常上报等待。

每个回合之后，后台工作最多有 30 分钟完成。到限时，shell 任务被杀死，工单上报等待。报告包含执行器最后的话，以及哪些任务被杀死、哪些子代理仍在运行。子代理被允许继续。执行器在下一回合读取被杀死任务的结果。

向人的交接会立即释放槽位并让报告保持生效。这适用于 `ready` 报告或一个提问之后（除非此后又来了别的输入），以及任何 `blocked` 或 `failed` 报告之后。

交接时，子代理停止。shell 任务（例如供评审而启动的服务）可以继续到派工结束。它们不占槽位，也不受 30 分钟限制约束，包括其后的回合。它们的完成不唤醒执行器；执行器在下一回合读取结果。

人也可以直接在执行器 Session 里输入来启动一个回合。其后台工作遵循同样的规则。

派工结束时，其 shell 任务被杀死且不唤醒 Session。其子代理被释放，它们唤醒的任何完成回合都被丢弃。替代的派工及其等待中的输入在那次关闭完成之后启动。

在 DeepSeek Harness 进程内停止或重启插件走同一条关闭路径。尚未进入 Session 历史的输入会被保留。关闭为每个执行器的后台工作最多等待 10 秒；进程重启则直接终止这些工作。忙碌中被中断的派工带着恢复说明重启。

执行器的子代理（包括嵌套的）使用 DeepSeek Harness 的 `standard` preset，并继承执行器的权限。它们只保留执行器获准的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令 60 秒后转入后台。子代理结束时其任务被杀死。

### 准备工单目录

第一次派工之前，如果工单目录不存在，prepare 命令以 `sh` 在执行根目录运行一次。限时十分钟。没有 prepare 命令时，执行器在空目录中开始。

失败的命令使工单失败并记录其输出。重试，或人的消息到达工单的某个线程，都会再次尝试准备。典型命令用 `git worktree` 创建检出。当一个拉取请求分支的最后一段路径与工单短名一致时，它属于该工单。

### 并发

工单从一次启动（包括准备）开始、或从唤醒其空闲执行器的投递开始，持有一个执行器槽位。活跃回合期间也持有槽位。

配置的并发上限作用于这些槽位，另有一个额外槽位留给人的消息或状态请求。普通槽位占满时，这类唤醒可以使用额外槽位，并且在新启动之前优先取得下一个空闲槽位。因此新工作无法阻止人继续一个已有工单。

其他输入（例如 CI 结果）等待普通槽位。启动在 `working / queued` 中等待槽位空闲。启动并发运行，所以缓慢的 prepare 命令只拖延自己的工单。

### 执行变量

prepare 命令与执行器指令收到同样的执行变量。命令从环境变量读取；执行器在其提示词中读取值与描述。任何变量都不含凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名与 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | Source 监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起工单的 Issue 或拉取请求，以及拉取请求的头引用 |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及发起工单的聊天 |

工单专属的值来自其目录与来源触发。其余值来自当前部署设置。只有面板能更改执行环境设置；发给主 Session 的文本不能更改配置的 shell 命令。

执行器经智能体账号的 `gh` 访问 GitHub，经机器人的 `lark-cli` 访问飞书。被禁止的命令按名称调用时失败。

这些包装与目录建立的是默认值，不是安全边界。执行器仍可以用绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词约束。宿主没有针对合并的决定逻辑。

默认情况下，执行器绝不以智能体账号开启自动合并：GitHub 会把合并记在开启者名下。交付要求必须指名另一个账号的 CLI 来合并。没有时，由人来合并拉取请求。

默认指令只对为工单打开的拉取请求允许自动合并，且要求：已就绪、所需批准覆盖头提交、新增加删除合计少于 200 行。推送新版本之前，执行器先撤回自动合并。

没有正文的评审（例如批准）也会作为触发到达，可以唤醒等待评审的执行器。这些指令约束的是智能体，不是 GitHub 的合并规则。要强制批准，请在分支保护中要求批准并驳回过期批准。省略合并 CLI 或删除自动合并段落即可要求手动合并。

## 工单如何结束

- **就绪且没有拉取请求：** `ready` 报告以已完成结束工单。
- **无事可做：** 执行器发现没有任何需要人行动的事（例如无法复现或已被取代的请求），上报 `dropped`。工单不发消息即结束，除非匹配的规则要求一条；人此后在其线程上的消息会恢复它。
### 拉取请求

执行器上报后，工单跟随它起始自的那个拉取请求。它也跟随从其分支打开的每个拉取请求——由执行器上报或被 GitHub Source 发现。重新打开的拉取请求会被再次跟随。

当它打开的拉取请求没有一个仍开启时，工单完成。若它一个也没打开，则其跟随的所有拉取请求都必须关闭。此时它以最后一次相关关闭的结果结束，并保留其订阅，让之后的人的评论能恢复它。

被恢复、重试或恢复中的工作未完成时，一次关闭不会结束工单。如果执行器确认或回答了其持有的一条跟进、且此后没有做非进展报告或结束回合，工单也会等待。稍后的 `ready` 报告在同样的拉取请求完成规则满足后结束工单。

聊天渠道会收到一条关于拉取请求结果的终态通知。GitHub 上拉取请求本身已显示结果。移除工单对某个拉取请求的订阅，也会停止跟随该拉取请求。

因此"等待评审"意味着一份带拉取请求的 `ready` 报告。

### 跟进与上下文线程

执行器决定其工单自己线程上人的跟进。它处理范围内的请求，交回超出其范围或属于其他工单的请求。一旦没有执行器持有该消息，它就成为主 Session 的候选。此外，主 Session 对跟进的唯一处理动作是应人的请求停止工作。

一个输入在 Session 把它纳入某一步骤、随后做出报告或结束回合之后，才算已读。工单结束时，未被确认、回答或交回的未读消息回到评估，如 [002 授权](002-authorization.md) 所述。已读但未处理的消息（例如致谢）不回到评估。

仅为上下文关注的线程仍然投递消息，但不给工单对人的跟进的持有权，也不恢复已结束的工单。那些消息可以被独立评估。

在存活工单订阅期间，以及自最后一个触发和订阅工单的结束两者中较晚者起两周内，Source 轮询被订阅的线程。此后消息只经普通接入到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 上报 `blocked` 或 `failed`，或启动失败/出错（记录为 `failed`）时，工单不再自动接收输入。

模型服务或网络的瞬时失败、HTTP 408、429 或 5xx、被拒、重置或超时的连接，会先重试三次并逐步加长退避：启动会重新运行，回合失败的执行器会被指示继续；失败的 prepare 命令不会重试。

一旦失败，CI 和机器人消息会记录在工单上，但不投递，也不唤醒 Session。

其工具保持可用，人可以在 Session 中直接继续。

失败的启动不会自行重试。

人的消息、一份既非 `blocked` 也非 `failed` 的后续报告，或一次重试会解除暂停。

暂停状态由已存储的报告与输入推算，因此重启后仍然保持。
### 重试

在开启的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用： remedy 是一次新的派工，它重新启动执行器并接收等待中的输入。

一旦人的消息到达了 blocked 或 failed 的工单，执行器已持有该消息，工单显示为执行中（失败的启动重新运行时为排队中），且不再提供重试——除非该消息的投递失败了。

重试结束当前派工，并在同一执行器 Session、目录、分支和拉取请求中开始新的派工。

执行器模型只在 Session 创建时生效；已有 Session 保留其模型。
### 重启

在跑的派工以"宿主重启"结束，新的派工带着恢复说明启动，指示执行器在重复任何外部动作之前先检查其目录、git 历史和 GitHub；最老的工单先重启。

等待、就绪、受阻或失败的派工保持原样，除非在该报告之后有输入到达——那样它们也会重新启动。

Session、目录、订阅、待处理消息和下述存储的工作都会在重启后保留；每个执行器 Session 把哪些消息纳入了历史的记录同样保留——步骤在认领它们之后、模型调用之前记录：被重启切断的回合所认领的消息，在其后有报告或回合结束时算作已读；而步骤认领了、但历史记录之前被取消或错误切断的消息算作未读。

重试或重启会让新派工再次收到被替代派工收到、但其执行器 Session 未纳入的消息（取消或被切断的步骤可能丢失的那些）；仍留在 Session 中的一份副本——由重启保留或跨崩溃持久化——会在新派工的第一条消息之前被取出，使新投递成为唯一的副本。
### 存储的工作

dsh-superagent-cn 在决定之后所做的事，例如向主 Session 转发候选、跟进或报告，启动派工，或投递输入，都先存储再执行。

失败的转发或投递（例如其 Session 不可达）在 2 秒后重试，随后按加倍延迟直到一分钟；失败的启动使其工单失败，除非如上所述是瞬时失败。

每一类工作只有在其中一个条目连续失败三次之后，才在总览的系统问题中报告错误；一次失败的输入投递则显示在其工单上。

向主 Session 的转发保持顺序，通知也一样；失败的一项会扣住同类后续项。
### Source 失败

GitHub Source 独立读取每个 Issue、拉取请求和线程：一次失败的读取把错误留在其线程上，在下次轮询时重读，并计入 Source 的错误——默认连续三次轮询失败后上报；任何一次成功都会清零。

GitHub 在智能体失去私有仓库访问权时也回答 404，因此 404 会被重试。

一个被通知的 Issue 或拉取请求，若读取持续失败，会在首次失败一天后被丢弃；GitHub 报告其已删除时立即丢弃。此后它不再使轮询失败，其线程保留错误，Source 的状态指名它。

其读取位置保持不变，所以稍后的通知或对其线程的轮询会读到失败读取错过的内容。

飞书事件消费者上报每一次失败，订阅话题的轮询把每次失败留在其线程上。

GitHub 列表或飞书分页中格式错误的条目被跳过，并计入 Source 的状态。
### 渠道失败

发出的消息作为存储工作保存，从 5 秒起以退避重试，加倍直到 300 秒。

同一工单发往一个会话的消息按排队顺序发出，因此其确认先于其后的回答或结果：当同一工单发往同一会话的更早一条尚未发出时，消息会等待，直到那一条连续失败三次并显示为问题。

其他工单的消息，以及不属于任何工单的消息，不会等它。

有失败尝试的消息是一个系统问题，直到发出或撤回。

只有当其 Source 不再监听该会话，或 Source 回答该会话永远无法接收时，消息才被丢弃；其 Source 关闭期间，消息等待。

对 GitHub 上已删除的 Issue 或被锁定的会话，以及飞书上被撤回或已找不到的消息，Source 会这样回答。

对已不存在的评审评论的回复改发到该拉取请求的会话。

被丢弃的消息保留记录，包括何时、为何被丢弃以及所属工单，因此绝不会再排队；被丢弃的确认读作 dropped，而不是 sent。
### 暂停处理

暂停会停止派发、新的评估、评估超时、输入投递和回复；已在进行的启动等待处理恢复。

Source 继续记录触发，运行中的执行器回合不被打断。

人发给已结束工单的消息会等待：暂停后的首轮处理会恢复该工单——如果其授权在当时的策略下仍然成立。

进行中的评估在暂停期间不过期；其截止时间按暂停时长顺延。
### 无效配置

被其 kind 拒绝的已存储 Source 配置会禁用该 Source 实例。
